## Not done

1. ~~The handlers are not transcribed.~~ **Done** — see note 07. Field `[49]`
   holds three dispatch tables (`h` 0..95, `Z` 0..29, `v` 0..49); every
   opcode now has its verbatim handler in `work/decompiled/vm_isa.md`. What is
   still missing is the *round trip*: an interpreter that executes those
   handlers against the dumped tables, which is the next step for (3).
2. **The proto table is not mapped.** We have the per-proto buffers and their
   indices (`02 <idx> 1f …`), but not the mapping idx → Luau function or the
   constant pools they reference.
3. **No full plaintext of the payload.** Bytecode is only decrypted lazily,
   block by block, while the VM runs; decrypting it offline needs the handler
   semantics from (1) because the keystream index is carried inside the VM's
   C/S-box state, which the loader mutates as it goes.
4. **The application logic is unknown.** All we know is the environment it
   targets and that it starts by showing an ASCII banner. Whether it is a
   hub/cheat loader, a key system, or an obfuscator self-test cannot be
   determined without finishing (1)–(3).

## Honest assessment of effort left

Steps (2)+(3) are the whole remaining job and they are *bulk*, not difficulty:
~170 small functions to normalise, then an interpreter over the decoded proto
stream. At the observed rate (≈85 k byte writes/s, ~250 MB of mixing left) a
complete *dynamic* run takes hours, so the practical route is static:
transcribe the handlers, then run them in a normal Luau interpreter against the
dumped tables (all of which are in `work/dumps/`).

## What would help

* If the original script came from a known source, `debug.info` symbols or a
  Roblox-side trace would shortcut step (2) enormously.
* Any known-plaintext from the payload (e.g. a screenshot of the banner in situ,
  or the script's UI text) would let us validate decrypted blocks immediately.
